# Счета

Счета — основа ApiPay.kz. Каждый счёт представляет запрос на оплату, который вы отправляете клиенту.

## Создание счёта

**Эндпоинт:** `POST /invoices`

Поддерживает два режима: фиксированная сумма или корзина товаров.

### Запрос (фиксированная сумма)

```bash
curl -X POST https://api.apipay.kz/api/v1/invoices \
  -H "X-API-Key: YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "amount": 10000,
    "phone_number": "87001234567",
    "description": "Оплата заказа #123",
    "external_order_id": "order_123"
  }'
```

### Запрос (с корзиной товаров)

Для организаций с подключённым каталогом:

```bash
curl -X POST https://api.apipay.kz/api/v1/invoices \
  -H "X-API-Key: YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "phone_number": "87001234567",
    "description": "Заказ из каталога",
    "cart_items": [
      {"catalog_item_id": 101, "count": 2, "price": 4500.00},
      {"catalog_item_id": 205, "count": 3}
    ],
    "discount_percentage": 10
  }'
```

Сумма рассчитывается автоматически из цен товаров каталога. Поддерживает кастомные цены и скидки.

### Параметры

| Поле | Тип | Обязательно | Описание |
|------|-----|-------------|----------|
| `amount` | number | Да* | Сумма в тенге, **только целая**: 1 - 99 999 999. Дробная → `422 amount_must_be_whole_tenge`; проверяется и `amount`, и итог `cart_items` после скидок. Нужны тиыны — используйте `POST /invoices/qr` (но со скидкой QR не принимает позиции с ценой в тиынах — `422 qr_discount_unsupported`). *Не обязательно при наличии cart_items. |
| `phone_number` | string | Да | Телефон клиента (формат: 8XXXXXXXXXX) |
| `description` | string | Нет | Описание платежа (макс. 60 символов — Kaspi показывает покупателю только первые 60) |
| `external_order_id` | string | Нет | Ваш ID заказа для сопоставления (макс. 255 символов) |
| `buyer_bin` | string | Нет | ИИН/БИН покупателя — строка ровно из 12 цифр, например `"buyer_bin": "012345678901"`. Числом не передавайте — потеряется ведущий ноль; иначе `422` с `errors.buyer_bin`. Kaspi номер не проверяет — проверьте все 12 цифр до отправки. Если у организации подключена Kaspi Касса, номер попадёт в чек Kaspi. Возвращается в ответе создания, в `GET /invoices` и `GET /invoices/{id}`; в вебхуках его нет. В `POST /invoices/bulk` номер задаётся в каждой строке (отказ — `errors.invoices.N.buyer_bin`) |
| `cart_items` | array | Нет | Массив товаров корзины (заменяет amount) |
| `discount_percentage` | number | Нет | Глобальный % скидки (1-99). Применяется ко всему чеку. |

### Поля товара корзины

| Поле | Тип | Обязательно | Описание |
|------|-----|-------------|----------|
| `catalog_item_id` | integer | Да | ID товара из каталога (из GET /catalog) |
| `count` | integer | Да | Количество (мин. 1) |
| `price` | number | Нет | Кастомная цена (0.01 - 99999999.99). Заменяет каталожную цену. |

### Ответ

```json
{
  "id": 124,
  "amount": "9500.00",
  "status": "processing",
  "paid_at": null,
  "phone": "87001234567",
  "is_imported": false,
  "created_at": "2026-01-31T12:00:00+00:00",
  "subtotal": "10000.00",
  "discount_sum": "500.00",
  "discount_percentage": "10"
}
```

> **Примечание:** Номер плательщика в ответе — поле `phone` (в запросе — `phone_number`). `description` и `external_order_id` ответ создания не повторяет — они есть в `GET /invoices/{id}`. Условные поля появляются только при наличии значения: `subtotal`, `discount_sum` и `discount_percentage` — при скидке или корзине, `buyer_bin` — если передан, `error_message` — при статусе `error`. `is_imported: true` — продажа подтянута из истории Kaspi (проведена в приложении мимо ApiPay).

`201` со `status: processing` — это не ошибка: финальный статус (`pending` или `error`) придёт вебхуком `invoice.status_changed` или по `GET /invoices/{id}`. Не пересоздавайте счёт в `processing`. Защита от дублей при ретрае — поле `external_order_id_idempotency`: повтор отвечает `409 duplicate_idempotency_key` с id прежнего счёта.

## Создание QR-счёта (на экране кассы)

**Эндпоинт:** `POST /invoices/qr`

Оплата по QR-коду на экране кассы — без номера телефона клиента. Касса показывает QR, покупатель сканирует приложением Kaspi и оплачивает. Подходит для оффлайн-точек, касс, торговых терминалов.

В отличие от обычного `POST /invoices`:
- Не нужен `phone_number`.
- Ответ синхронный — возвращается готовый QR (`qr_token_url` + PNG-изображение).
- Жизненный цикл QR-счёта — **минуты** (vs 24 часа у обычного, по номеру телефона). Точный момент истечения диктует Kaspi; терминальный статус (`paid`/`cancelled`/`expired`) приходит вебхуком. Поле `qr_expires_at` — справочно, не для локальной терминализации.
- Отмена QR-счёта не поддерживается — если оплата не пришла, счёт через несколько минут переходит в `expired` (по терминалу от Kaspi). Возврат по оплаченному QR-счёту — обычный `POST /invoices/{id}/refund`, как у любого счёта; если Kaspi потребует подтверждения покупателя, выпустите ему ссылку `POST /qr-refunds/links` (см. [Возвраты → Запасной путь](refunds.md#запасной-путь-ссылка-покупателю)).
- Per-org rate limit: **200 QR-запросов в минуту на организацию** — один счётчик на все её ключи, отдельно от общего лимита API (200 запросов в минуту на ключ).

> ⚠️ **QR-счёт — только для оплаты сразу.** Выставляйте `POST /invoices/qr`, когда покупатель рядом и платит прямо сейчас: QR живёт несколько минут. Если покупатель заплатит позже, используйте статический QR (`POST /static-qr`) или ссылку на оплату (`POST /invoices/qr` с `static: true`). Подробнее — в разделе «Какой QR выбрать» ниже.

> ℹ️ **QR-счета сосуществуют.** Создание нового QR на той же кассе **не отменяет** прежние — старый QR остаётся в статусе `pending` и мониторится до своего терминала. Реагируйте на `paid`/`cancelled`/`expired` по каждому `invoice.id` отдельно (при оплате нескольких QR придёт несколько `paid`). Счета по номеру телефона живут 24 часа в Kaspi.

Тело запроса зависит от настройки организации (`has_catalog`):

### Запрос (без каталога)

```bash
curl -X POST https://api.apipay.kz/api/v1/invoices/qr \
  -H "X-API-Key: YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "amount": 5000,
    "description": "Заказ №123",
    "external_order_id": "order-123"
  }'
```

### Запрос (с каталогом)

```bash
curl -X POST https://api.apipay.kz/api/v1/invoices/qr \
  -H "X-API-Key: YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "description": "Заказ №123",
    "cart_items": [
      {"catalog_item_id": 608400, "count": 2, "price": 1500}
    ],
    "discount_percentage": 10
  }'
```

### Параметры

| Поле | Тип | Обязательно | Описание |
|------|-----|-------------|----------|
| `amount` | number | Да* | Сумма (только если has_catalog=false), 0.01 - 99 999 999.99 ₸ |
| `description` | string | Нет | Описание (макс. 100). Используется как наименование позиции в QR-чеке Kaspi |
| `external_order_id` | string | Нет | Ваш ID заказа (макс. 255) |
| `cart_items` | array | Да* | Только если has_catalog=true. От 1 до 100 позиций |
| `discount_percentage` | integer | Нет | Скидка в процентах — **только целое число** 1–99; дробное → `422` с `errors.discount_percentage`. Скидка каждой строки округляется **вверх** до целого тенге, см. [Скидка на QR](#скидка-на-qr) |
| `buyer_bin` | string | Нет | ИИН/БИН покупателя — по тем же правилам, что в `POST /invoices`: строка ровно из 12 цифр, иначе `422` с `errors.buyer_bin`. Со `static: true` не принимается (`422`). Если у организации подключена Kaspi Касса, номер попадёт в чек Kaspi |
| `simulate` | string \| object | Нет | Только для песочницы: строка `paid` \| `cancelled` \| `expired` или объект `{"status": "error", "error_code": …}`. Со `static: true` запрещено. См. [Sandbox-режим](#sandbox-режим) |

\* зависит от `has_catalog`: либо `amount`, либо `cart_items`.

### Скидка на QR

Скидка на QR-счёте считается по правилу Kaspi, а не как «процент от суммы»:

- процент — только целый, от 1 до 99;
- скидка каждой строки корзины = `цена × количество × процент / 100`, округлённая **вверх** до целого тенге;
- к оплате — сумма строк минус сумма скидок.

Поэтому на дешёвой позиции фактическая скидка больше заявленной — так же считает приложение Kaspi:

| Корзина | Скидка | Скидка по строкам, ₸ | К оплате, ₸ |
|---|---|---|---|
| 5 ₸ × 1 | 10 % | 1 | 4 |
| 5 ₸ + 10 ₸ | 20 % | 1 + 2 | 12 |
| 5 ₸ + 10 ₸ | 7 % | 1 + 1 | 13 |
| 5 ₸ × 3 | 7 % | 2 | 13 |

Сумму счёта берите из ответа (`amount`, `discount_sum`), а не из своего расчёта. Если считаете заранее — ровно по этому правилу. У счёта по номеру телефона (`POST /invoices`) скидка считается иначе, поэтому одну формулу на оба вида счёта не заводите.

Отказ `422 qr_discount_unsupported` значит, что скидку к этой корзине применить нельзя; счёт не создаётся, в песочнице так же. Причины:

- цена позиции задана в тиынах — в `cart_items[].price` или в каталоге;
- скидка обнуляет позицию: 1 ₸ со скидкой 10 % — это скидка 1 ₸.

Количество в строке корзины — не больше 100 000 (`422` с `errors.cart_items.N.count`). То же правило скидки действует для `static: true` и для печатного листа `POST /static-qr`. Цену позиции без `price` лист и ссылка на оплату берут из каталога в момент оплаты, а не при выпуске: если она станет дробной, лист со скидкой перестанет принимать оплату. Задавайте цену полем `price` в строке корзины — в целых тенге. Лист с корзиной и скидкой оплачивается только по QR: оплаты по номеру телефона на его странице нет. На листе без корзины (с `amount`) скидка не применяется.

### Ответ 201

```json
{
  "id": 63474,
  "amount": "100.00",
  "status": "pending",
  "paid_at": null,
  "phone": null,
  "created_at": "2026-05-09T07:27:37+00:00",
  "is_qr_token": true,
  "qr_token_url": "https://qr.kaspi.kz/0000000000000000000000000000000000000000",
  "qr_image_url": "https://api.apipay.kz/storage/qr/00000000-0000-0000-0000-000000000000.png",
  "qr_expires_at": "2026-05-09T07:32:38+00:00"
}
```

| Поле | Описание |
|------|----------|
| `id` | ID счёта в нашей системе. По нему получать статус (`GET /invoices/{id}`) и приходят webhook-уведомления. |
| `is_qr_token` | Флаг QR-счёта. Также возвращается в `GET /invoices/{id}`; в теле вебхука его нет. |
| `qr_token_url` | Ссылка Kaspi на этот QR-счёт. Та же информация, что закодирована в PNG: её можно открыть на телефоне покупателя вместо скана или перерисовать QR в своём стиле. Живёт столько же, сколько QR, — «на потом» не отправляйте. |
| `qr_image_url` | Готовый PNG 600×600 с логотипом Kaspi в центре (ECC=High). На нашем CDN-storage, доступен без авторизации, живёт `qr_expires_at` + 60 сек (после этого 404 — выпустите новый счёт). Тот же адрес приходит в `GET /invoices/{id}`. |
| `qr_expires_at` | Крайний момент, когда QR ещё можно **отсканировать** (UTC). Длительность окна задаёт Kaspi — считайте её из этого поля, а не константой. Окно ограничивает только скан: оплата, начатая под конец окна, завершится уже после `qr_expires_at`. Терминальный статус диктует Kaspi — ждите вебхук, а не локальный отсчёт. |

### Жизненный цикл и обработка статуса

1. После создания счёт в статусе `pending`. Сервис сам отслеживает изменение статуса на стороне Kaspi.
2. При смене статуса на терминальный (`paid`, `cancelled`, `expired`) прилетает обычный webhook `invoice.status_changed` — точно такой же по формату, как для обычных счетов. QR-полей и `is_qr_token` в нём нет: если они нужны, читайте `GET /invoices/{id}`.
3. Альтернативный poll: клиент может опрашивать `GET /invoices/{id}` каждые 2-3 сек.
4. Через несколько минут без оплаты статус становится `expired` — но только когда Kaspi отдал терминал (вебхуком), а не по локальному таймеру. PNG исчезает из storage в течение минуты — `qr_image_url` начнёт возвращать 404.
5. Отмена QR-счёта не поддерживается — просто дождитесь истечения (несколько минут). Возврат по оплаченному QR-счёту — `POST /invoices/{id}/refund`, при отказе с требованием подтверждения покупателя — ссылка `POST /qr-refunds/links` с `source_refund_id`. Немедленный `POST /qr-refunds` с QR у кассы — deprecated.

### Какой QR выбрать

| Ситуация | Что выставлять |
|---|---|
| Покупатель рядом и платит прямо сейчас | QR-счёт: `POST /invoices/qr` |
| Покупатель заплатит позже: подумает, получит ссылку в мессенджере, оплатит по бумаге | Статический QR (`POST /static-qr`) или ссылка на оплату (`POST /invoices/qr` с `static: true`) |

- **QR-счёт живёт несколько минут.** Точное окно задаёт Kaspi, оно приходит в `qr_expires_at`. Если покупатель не успел, счёт переходит в `expired`, и для оплаты нужен новый QR.
- **В рабочем режиме каждый выпущенный QR-счёт занимает место в дневном лимите тарифа** — в любом статусе, в том числе истёкший без оплаты и каждый пересозданный; место не возвращается. При систематическом превышении лимита создание отклоняется с `429 tariff_limit_reached`.
- **У статического QR и ссылки на оплату счёт создаётся, только когда покупатель нажал «Оплатить в Kaspi».** Пока покупатель думает, место в лимите не занято.
- **После нажатия «Оплатить в Kaspi» выпущенный Kaspi-QR тоже занимает место в лимите.** У одноразового кода (так по умолчанию; ссылка на оплату всегда одноразовая) повторное нажатие, пока этот QR действует и не отсканирован, возвращает тот же QR. У многоразового статического QR (`single_use: false`) каждое нажатие выпускает новый счёт, и каждый занимает место в лимите. Если QR истёк, выпускается новый счёт — и он занимает ещё одно место.

> 💡 **Правило для ИИ-агента и интегратора.** `POST /invoices/qr` без `static` — только если покупатель платит сразу. Для оплаты «на потом» — статический QR (`POST /static-qr`) или ссылка на оплату (`POST /invoices/qr` с `static: true`). Не пересоздавайте QR-счёт по таймеру в ожидании покупателя.

### Sandbox-режим

Если у организации `sandbox_mode=true`, эндпоинт работает БЕЗ обращения к Kaspi: `qr_token_url` ведёт на тестовую страницу ApiPay (`https://qr.apipay.kz/sandbox/…`), которая показывает сумму, описание и статус счёта, а PNG реально отрисован и кодирует тот же адрес. Его можно отобразить в UI и протестировать всю фронтенд-логику, но оплатить такой счёт в Kaspi нельзя. Путь адреса не разбирайте — его формат не входит в контракт; признак песочницы — `is_sandbox`. Без `simulate` песочный QR истекает сам после `qr_expires_at` (статус `expired` и вебхук).

#### Параметр `simulate` (только sandbox)

Для быстрого теста терминальных сценариев можно передать `simulate` прямо в теле создания — клиент в одном вызове получает уже готовый завершённый счёт нужного статуса (без необходимости отдельной ручки `/simulate-status`):

| `simulate` | Результат | Вебхук |
|------------|-----------|--------|
| (не передан) | `pending`; после `qr_expires_at` счёт сам станет `expired` | при истечении |
| `expired` | `expired` | да |
| `paid` | `paid` | да |
| `cancelled` | `cancelled` | да |

Объект `{"status": "error", "error_code": "kaspi_error" | "qr_render_failed" | "kaspi_session_invalid"}` даёт синхронный отказ теми же ответами, что в бою (`502`, `500`, `503`), и вебхук `error`.

- У боевой организации строковое значение игнорируется молча, а объект отклоняется `422`.
- Со `static: true` поле запрещено. Неизвестные значения → 422.
- Все способы заказать исход — [Песочница](sandbox.md).

##### Пример: получить уже истёкший QR

```bash
curl -X POST https://api.apipay.kz/api/v1/invoices/qr \
  -H "X-API-Key: <sandbox_api_key>" \
  -H "Content-Type: application/json" \
  -d '{"amount": 250, "simulate": "expired"}'
```

Ответ (фрагмент):

```json
{
  "id": 63497,
  "status": "expired",
  "is_qr_token": true,
  "qr_token_url": "https://qr.apipay.kz/sandbox/…",
  "qr_image_url": "https://api.apipay.kz/storage/qr/….png",
  "qr_expires_at": "2026-05-09T07:52:08+00:00"
}
```

Отдельно `POST /invoices/{invoice}/simulate-status` тоже работает с QR-счетами (для динамических сценариев: создал `pending` → подождал в UI → явно перевёл в `paid`/`cancelled`/`expired` или изобразил скан `qr_scanned`).

### Ошибки

| Код | error | Когда |
|-----|-------|-------|
| 400 | `organization_required` | У api-key нет организации |
| 400 | `kaspi_session_not_configured` | У организации не подключён кассир Kaspi (Настройки → Авторизация Kaspi) |
| 400 | `Organization not found or not verified` | Боевая организация в статусе ≠ `verified` |
| 400 | `sandbox_invoice_limit` | Превышен лимит sandbox-счетов |
| 422 | `Validation failed` | Невалидные параметры (см. body schema) |
| 422 | `catalog_requires_cart_items` | `has_catalog=true`, но `cart_items` не передан |
| 422 | `catalog_not_supported` | `has_catalog=false`, но передан `cart_items` |
| 422 | `qr_discount_unsupported` | Скидку нельзя применить к корзине: цена позиции в тиынах или скидка обнуляет позицию. Код приходит и в `error`, и в `error_code`, текст причины — в `errors.discount_percentage`. Счёт не создан. См. [Скидка на QR](#скидка-на-qr) |
| 422 | — | В корзине есть позиция в статусе `deleting`; причина — в `errors["cart_items.N.catalog_item_id"]`, отдельного `error_code` у этой ветки нет. Верните позицию или уберите её из корзины, см. [Каталог → Статусы товара](catalog.md#статусы-товара) |
| 429 | `qr_rate_limit` | Per-org лимит 200 QR/мин, без `Retry-After` — повторите примерно через минуту |
| 500 | `qr_render_failed` | Не удалось отрисовать PNG |
| 502 | `kaspi_error` | Kaspi API вернул ошибку |
| 503 | `kaspi_session_invalid` | Сессия Kaspi истекла |

> Два кода паритета каталога приходят в поле **`error_code`**, а не `error`, и без объекта `errors` — рядом лежит только `message`. Тексты `message` при их появлении не менялись, так что разбор по строке продолжает работать; переводите ветвление на `error_code`.

## Ссылка на оплату и печатный QR

Для оплаты «потом» — когда покупатель подумает, получит ссылку в мессенджере или оплатит по бумаге:

- **Ссылка на оплату** — `POST /invoices/qr` со `static: true`. В ответе `payment_url` (отправьте покупателю или поставьте кнопкой на сайте) и `static_qr_id`. Нужен действующий тариф. Повтор с тем же `external_order_id_idempotency` отвечает `409 idempotency_conflict` с той же ссылкой.
- **Печатный лист** — `POST /static-qr`. В ответе `print_url` (адрес листа, его кодирует QR), `short_code` для ручного ввода, `qr_image_url` и `payment_url` — ссылка на оплату той же сделки. Отключить — `DELETE /static-qr/{id}`: новые сканы покажут «неактивно», уже созданные счета не трогаются.

**Счёта при выпуске нет.** `static_qr_id` — не ID счёта, в `GET /invoices/{id}` его не передавайте. Счёт — попытка оплаты — создаётся, только когда покупатель нажал «Оплатить» на странице; открытие страницы и предпросмотр в мессенджере счёт не создают. У одной ссылки или листа может быть несколько попыток.

### Лимит тарифа

| Действие | Место в дневном лимите |
|---|---|
| `POST /invoices`, `POST /invoices/qr`, каждая строка `POST /invoices/bulk`, каждый счёт подписки, созданной через API | занимает — в любом статусе, место не возвращается |
| Выпуск ссылки `static: true` или листа `POST /static-qr` | не занимает |
| Открытие страницы ссылки или листа, предпросмотр в мессенджере | не занимает |
| Нажатие «Оплатить» на странице (новая попытка) | занимает — каждая попытка |
| Песочница, счета из кабинета | не занимают |

Лимит тратит каждый счёт, созданный вашим ключом, — оплаченный, истёкший, отменённый или с ошибкой. Пока покупатель думает над ссылкой или листом, место не занято; каждая попытка после нажатия «Оплатить» занимает место. У одноразовой ссылки или листа повторное нажатие, пока выпущенный QR действует и не отсканирован, нового счёта не создаёт; у многоразового листа (`single_use: false`) каждое нажатие — новый счёт. Если QR истёк неотсканированным, открытая страница сама выпустит новый счёт без нажатия — и он тоже займёт место. Лимит тарифа — до 30, до 100, до 300 или до 600 счетов в сутки в зависимости от тарифа; расход видно в `GET /tariff` → `daily_usage`. При систематическом превышении создание отклоняется `429 tariff_limit_reached`. Пока действует такое ограничение, подписка, созданная через API, счёт за период не выставляет: дата следующего счёта не сдвигается, пропущенные периоды не догоняются.

### Как сопоставить оплату с заказом

Оплата приходит вебхуком `invoice.status_changed` попытки, `invoice.id` которой заранее неизвестен:

1. Заказ ищите по `invoice.static_qr_id` (синоним `static_qr_code_id`), затем по `external_order_id`. При первой оплате сохраните `invoice.id` — по нему делается возврат.
2. `expired`, `cancelled` и `error` попытки **не отменяют заказ**: ссылка или лист живы, покупатель может нажать «Оплатить» снова. Истечение попытки — не отмена заказа.
3. Тот же `invoice.id` с тем же статусом — повтор доставки. **Другой `invoice.id` той же ссылки со статусом `paid` — вторые деньги покупателя**, а не дубль: верните их (`POST /invoices/{id}/refund` по этой попытке) или отдайте на проверку человеку.
4. Уведомления об истечении самой ссылки нет: срок заказа ведёт ваше приложение.

Для сверки все попытки одной ссылки или листа возвращает `GET /invoices?static_qr_id={id}`, итог — `GET /static-qr/{id}`. В песочнице попытку создаёт `POST /static-qr/{id}/simulate` (см. [Песочница](sandbox.md)).

## Получение счёта

**Эндпоинт:** `GET /invoices/{id}`

```bash
curl https://api.apipay.kz/api/v1/invoices/42 \
  -H "X-API-Key: YOUR_API_KEY"
```

> Ответ включает массив `items` — снимок товаров корзины при создании счёта: `[{ id, invoice_id, catalog_item_id, name, price, count, unit_id, discount, barcode, ntin, gtin }]`. Поля `subtotal`, `discount_sum`, `discount_percentage` — сумма до скидки и скидка, `null`, если скидки и корзины нет. У QR-счёта есть `qr_image_url` — абсолютный адрес картинки QR (`qr_image_path` оставлен для совместимости). У попытки оплаты по ссылке или листу — `static_qr_id`.

**Поле `kaspi_qr_link`** — ссылка на оплату этого счёта по QR вида `https://kaspi.kz/qr/pay?tranId=QR…`. Нарисуйте из неё QR-код покупателю. Поле есть и в каждом элементе `data` у `GET /invoices`. Вычисляется из идентификатора Kaspi и не хранится, поэтому приходит `null`, пока Kaspi этот идентификатор не присвоил (статус `processing`), и всегда `null` в песочнице.

> ⚠️ Не путайте `kaspi_qr_link` с `qr_token_url`: последний относится к отдельному механизму QR-счетов (`POST /invoices/qr`).

## Чек Kaspi по счёту

**Эндпоинт:** `GET /invoices/{id}/receipt`

Ссылки на чек Kaspi по оплаченному счёту — чтобы отдать чек покупателю.

> Это чек Kaspi по оплате счёта. Фискальные чеки за наличные и POS другого банка — отдельный раздел [Фискальные чеки](receipts.md) (Kaspi OFD), к этой ручке он отношения не имеет.

```bash
curl https://api.apipay.kz/api/v1/invoices/42/receipt \
  -H "X-API-Key: YOUR_API_KEY"
```

**Ответ асинхронный.** Первый вызов ставит задачу и отдаёт `202`:

```json
{ "status": "pending", "poll_after": 2 }
```

Повторите запрос через `poll_after` секунд — интервал берите из ответа, а не из своей константы. Как только чек получен, тот же URL отдаёт `200`:

```json
{
  "status": "ready",
  "receipt_link": "https://kaspi.kz/...",
  "download_link": "https://kaspi.kz/...&hash=...",
  "share_link": "https://kaspi.kz/...&hash=...",
  "sale_date": "2026-08-10 09:14:00.000000",
  "fetched_at": "2026-08-10T09:15:02+00:00"
}
```

`sale_date` приходит в том виде, в каком его отдал Kaspi (`ГГГГ-ММ-ДД ЧЧ:ММ:СС.мкс`), а не в ISO 8601; микросекунды значащие — не отбрасывайте их. Остальные поля времени — ISO 8601.

Готовый чек кэшируется: повторный запрос по тому же счёту отвечает сразу.

Ссылки различаются назначением: `share_link` — та, что предназначена покупателю; `download_link` — прямой PDF для вашей системы; `receipt_link` — фискальная форма чека, её можно показывать где угодно.

> ⛔ `download_link` и `share_link` содержат секретный параметр `hash` — по нему чек откроет кто угодно. Не публикуйте их, не кладите в логи и не подставляйте в URL своих страниц. Выданную ссылку отозвать нельзя: если она утекла, закрыть доступ нечем. `receipt_link` секрета не несёт.

Чек существует только у счёта в статусе `paid` или `partially_refunded` — частичный возврат остаётся оплаченным счётом. Вебхука на это событие нет: запрашивайте чек после перехода счёта в `paid`. В песочнице ручка отвечает сразу, а ссылки помечены `sandbox=1` — это заглушки, настоящего чека по ним нет, покупателю их отдавать нельзя.

**Ошибки:**

| Код | HTTP | Когда |
|-----|------|-------|
| `receipt_not_available_for_status` | 409 | Счёт не в `paid`/`partially_refunded`, либо у оплаченного счёта ещё нет числового идентификатора Kaspi |
| `kaspi_session_expired` | 409 | Кассир по счёту требует переподключения |
| `kaspi_session_unavailable` | 409 | Кассир временно недоступен |
| `receipt_rate_limited` | 429 | У ручки собственный минутный лимит, он строже общего |
| `receipt_unavailable` | 503 | Kaspi не отдал чек — обычно помогает повтор через минуту |

## Отмена счёта

**Эндпоинт:** `POST /invoices/{id}/cancel`

Можно отменить счета со статусом `pending` или `processing`. Счёт, ещё не переданный в Kaspi (без `kaspi_invoice_id`), отменяется синхронно — `200` и вебхук `cancelled`. Счёт, уже переданный в Kaspi, — `202 Accepted` со статусом `cancelling`: не считайте его отменённым сразу, итог придёт вебхуком. Если Kaspi отказал, счёт вернётся в `pending` без вебхука; актуальный статус придёт следующим вебхуком или будет виден в `GET /invoices/{id}`. **Песочница отменяет так же, как бой**; исход отмены в ней заказывается полем `simulate` (см. [Песочница](sandbox.md)).

> ⛔ **QR-счёт (`is_qr_token: true`) отменить нельзя — ни в бою, ни в песочнице:** запрос отвечает `409 qr_cancel_unsupported`, статус счёта не меняется. В теле ответа приходит `expires_at` — момент, после которого QR перестанет быть оплачиваемым. Дождитесь `expired` или выставьте новый счёт. Ссылку на оплату (`static: true`) и печатный лист отключают `DELETE /static-qr/{id}`.

```bash
curl -X POST https://api.apipay.kz/api/v1/invoices/42/cancel \
  -H "X-API-Key: YOUR_API_KEY"
```

### Ответ 202

```json
{
  "message": "Invoice cancellation queued",
  "invoice_id": 42
}
```

## Статусы счетов

| Статус | Описание | Можно отменить | Можно вернуть |
|--------|----------|----------------|---------------|
| `processing` | Ожидает отправки в Kaspi | Да | Нет |
| `pending` | Ожидает оплаты | Да | Нет |
| `cancelling` | Отменяется (асинхронно) | Нет | Нет |
| `paid` | Оплачен | Нет | Да |
| `cancelled` | Отменён вручную | Нет | Нет |
| `expired` | Истёк срок оплаты | Нет | Нет |
| `error` | Ошибка отправки в Kaspi (см. `error_message`) | Нет | Нет |
| `partially_refunded` | Частичный возврат | Нет | Да |

> Статуса `refunded` не существует: полный возврат статус не меняет — счёт остаётся `paid` (или `partially_refunded`, если ранее был частичный), а полнота возврата видна по `is_fully_refunded=true`.

## Переходы статусов

```
processing → pending → paid → partially_refunded
    ↓           ↓
  error    cancelling
                ↓
            cancelled

pending → expired
processing → cancelled (через cancel)
cancelled → paid, expired → paid (оплата в последний момент)
error → pending (сверка нашла живой счёт)
```

Последовательности `cancelled → paid`, `expired → paid` и `error → pending` законны и приходят вебхуком — не закрывайте заказ навсегда по `cancelled`, `expired` или `error`. Если после `error` вы уже выставили по заказу новый счёт, а старый вернулся в `pending`, отмените один из них. Подробнее — [Webhooks → Переходы статусов](webhooks.md#переходы-статусов).
