# Каталог

API каталога позволяет управлять товарами. Товары из каталога используются при создании счетов с корзиной (`cart_items`).

## Единицы измерения

**Эндпоинт:** `GET /catalog/units`

Возвращает доступные единицы измерения для товаров каталога.

```bash
curl https://api.apipay.kz/api/v1/catalog/units \
  -H "X-API-Key: YOUR_API_KEY"
```

Ответ: `{ "data": [{ "id": 1, "name": "шт", "name_kaz": "дана" }, ...] }`

## Список товаров

**Эндпоинт:** `GET /catalog`

Фильтры: `search`, `barcode`, `first_char`, `statuses[]` (можно несколько значений: `active`, `pending`, `deleting`, `deleted`, `failed`), `without_ntin`. Пагинация: `page`, `per_page` (1-200).

> ⚠️ **Без `statuses[]` отдаются только `active`.** Чтобы увидеть позиции в других статусах, перечислите их явно: `?statuses[]=active&statuses[]=deleted`. Так же проверяют, что удаление доехало до Kaspi.

**Точечное чтение.** Параметры `ids[]`, `external_refs[]`, `barcodes[]`, `ntins[]` возвращают конкретные позиции в любых статусах и без пагинации — форма `{"data": [...]}`. Ограничений два: суммарно не больше 200 значений по всем четырём наборам и не больше 1000 найденных строк соответствий. Превышение любого отдаёт `422` с `error_code: catalog_match_overflow` — разбейте запрос на части. Это штатный способ подтвердить результат заливки или удаления по своим кодам 1С.

Фильтр `without_ntin=true` возвращает только позиции без НТИН (`ntin` = `null`), независимо от наличия штрихкода — шире, чем поле ответа `ntin_missing` (оно требует непустой `barcode`). Удобно оценивать остаток «сколько позиций осталось доделать» по `meta.total`. Компонуется со всеми режимами и фильтрами.

Каждый товар в ответе содержит поле `created_at` — дата создания в системе (ISO 8601). Доступно сразу после создания, даже если Kaspi ещё не вернул `date_added`.

Каждый товар также содержит поле `gtin` (строка или `null`) — GTIN из Нацкаталога, если товар был создан с ним. Листинг Kaspi значение `gtin` не возвращает, поэтому синхронизация каталога его не затирает.

Кроме статуса у позиции есть отдельные поля `operation`, `error_code`, `error_message`, `sellable` и `in_kaspi_catalog` — см. [Статусы товара](#статусы-товара).

> ⛔ Фильтр `batch_id` удалён вместе с агрегатом партий и **отклоняется явно**: `422` с `error_code: catalog_batch_filter_removed`. Отбивается по самому наличию параметра — пустой `?batch_id=` тоже даёт `422`. Подтверждайте свой набор точечным запросом по `external_refs[]`.

## Загрузка изображения

**Эндпоинт:** `POST /catalog/upload-image`

```bash
curl -X POST https://api.apipay.kz/api/v1/catalog/upload-image \
  -H "X-API-Key: YOUR_API_KEY" \
  -F "image=@photo.jpg"
```

Формат: `multipart/form-data`. Только JPEG и PNG, макс. 6 МБ, стороны 64…6000 px, площадь до 12 Мпикс. Файлы gif, webp, bmp и svg отклоняются (`422 invalid_file_type`) — конвертируйте их на своей стороне. Файл больше 6 МБ — `413 file_too_large`. Лимит: 60 запросов в минуту и 2000 в сутки на ключ.

Ответ: `{"image_id": "550e8400-..."}`.

## Сканирование штрихкода (Нацкаталог)

**Эндпоинт:** `POST /catalog/scan`

Резолвит штрихкод в Нацкаталоге Kaspi и возвращает карточки товаров-кандидатов. Используйте перед созданием товара, чтобы подтянуть официальное название, НТИН и GTIN. Работает синхронно.

```bash
curl -X POST https://api.apipay.kz/api/v1/catalog/scan \
  -H "X-API-Key: YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"input": "4607015232646"}'
```

Поле: `input` (обяз., строка, макс. 64) — штрихкод, введённый вручную или полученный со сканера.

Ответ `200 OK`:

```json
{
  "data": [
    {
      "id": 1118196,
      "name": "ВАФЛИ ЯШКИНО ОРЕХОВЫЕ 300Г",
      "ntin": "0200009461097",
      "gtin": "4607015232646",
      "barcode": "4607015232646",
      "unit_id": null,
      "image_link": null
    }
  ],
  "normalized_barcode": "4607015232646",
  "scan_result": { "code": "ok", "message": null }
}
```

Один штрихкод может вернуть несколько кандидатов (общий `gtin`, разные `ntin`) — окончательный выбор делает продавец. Поля кандидата (`id`, `name`, `ntin`, `gtin`, `barcode`, `unit_id`, `image_link`) затем передаются в создание товара.

Если товар не найден — приходит `data: []` и/или `scan_result.code` отличный от `"ok"`. Это **не ошибка**: HTTP по-прежнему `200`. В этом случае создавайте товар обычным путём, без `ntin`/`gtin`.

> ⚠️ `normalized_barcode` — **эхо** присланного значения, и в бою, и в песочнице: не рассчитывайте, что поле что-то нормализует. НТИН и штрихкод — разные идентификаторы: сверка «`ntin` равен штрихкоду» неверна.

**Ошибки:**

| Код | Значение | Что делать |
|-----|----------|------------|
| `422` | `input` пустой или длиннее 64 символов | Исправьте ввод |
| `400` `kaspi_session_expired` | Сессия Kaspi истекла | Переподключите кассира Kaspi, затем повторите |
| `429` `kaspi_throttled` | Слишком часто (в теле `retry_after_seconds`, в заголовке `Retry-After`) | Подождите указанное время и повторите |
| `503` `kaspi_scan_unavailable` | Нацкаталог временно недоступен | Повторите позже |

**Лимиты:** 30 запросов/мин и 2000/сутки на API-ключ. Если Kaspi ограничил частоту, эндпоинт отвечает `429 kaspi_throttled` — дождитесь времени из `retry_after_seconds` (заголовок `Retry-After`) и повторите.

**Типовой сценарий:** сканирование штрихкода → `POST /catalog/scan` → показать `data[]` (если пусто — создать товар без `ntin`/`gtin`) → продавец выбирает кандидата → `POST /catalog` с `ntin`/`gtin`/`from_catalog: true` → товар создаётся в статусе `pending` → асинхронно уходит в Kaspi → `active`.

## Создание товаров

**Эндпоинт:** `POST /catalog`

Пакетное создание: 1–100 позиций за запрос.

```bash
curl -X POST https://api.apipay.kz/api/v1/catalog \
  -H "X-API-Key: YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"items": [{"name": "Кофе латте", "selling_price": 1500, "unit_id": 1, "image_id": "550e8400-..."}]}'
```

Поля: `name` (обяз., строка, макс. 255), `selling_price` (обяз., число, мин. 0.01), `unit_id` (обяз., целое), `image_id` (опц., UUID из `POST /catalog/upload-image`), `barcode` (опц., строка, макс. 32), `external_ref` (опц., строка, макс. 191) — ваша ссылка на позицию, например код номенклатуры 1С.

Поля Нацкаталога (опц., заполняются из выбранного кандидата `POST /catalog/scan`):

- `ntin` (строка, макс. 50) — НТИН выбранного кандидата.
- `gtin` (строка, макс. 50) — GTIN, только для кандидатов GS1.
- `from_catalog` (bool, по умолчанию `false`) — признак, что товар создан из Нацкаталога.

Пример элемента с данными Нацкаталога: `{"name": "ВАФЛИ ЯШКИНО ОРЕХОВЫЕ 300Г", "selling_price": 450, "unit_id": 1, "barcode": "4607015232646", "ntin": "0200009461097", "gtin": "4607015232646", "from_catalog": true}`.

**Используйте `external_ref` как ключ маппинга**, а не штрихкод и не имя: на один штрихкод у продавца может быть несколько товаров. По `external_ref` позиция потом читается точечно (`?external_refs[]=`), обновляется повторной заливкой `POST /catalog` и возвращается из очереди удаления. В `PATCH /catalog/{id}` поле `external_ref` не принимается — точечная правка идёт по `id`.

**Повторная заливка не создаёт дублей.** Если позиция совпала с уже существующим товаром, возвращается его живой `id` с маркером `matched_existing: true`. Совпадение ищется сначала по `external_ref`, затем по штрихкоду или НТИН вместе с именем. Если штрихкод совпал, а имя другое, позиция матчится без перезаписи имени и цены — маркер `name_differs: true`, имя правьте явным `PATCH /catalog/{id}`. `external_ref` существующего товара не перетирается никогда.

**Битая позиция не роняет запрос.** Каждая позиция валидируется отдельно: валидные уходят в `data[]`, отклонённые — в `rejected[]`. Ключ `rejected[]` присутствует в ответе всегда, в том числе пустым. `422` остаётся только за структурными ошибками самого запроса: `items` отсутствует, не массив, пуст или длиннее 100 позиций.

**Заголовок `Idempotency-Key`** (или поле `idempotency_key`, макс. 191 символ). Точный повтор того же тела в той же организации отвечает `200` с `idempotent_replay: true` и заново не выполняется.

> ⚠️ Пространство ключей идемпотентности **общее** с массовым удалением. Тот же ключ с другим телом либо на другой каталожной операции отдаёт `409 idempotency_key_conflict` — возьмите новый, повторять с тем же бесполезно.

**Код ответа:** всегда `202 Accepted` — «принято». В бою позиция получает статус `pending` и уезжает в Kaspi фоновой обработкой; в песочнице она возвращается уже активной. Форма ответа одна и та же в обоих контурах: `data[]` и `rejected[]`; у товара присутствует поле `gtin`.

## Обновление товара

**Эндпоинт:** `PATCH /catalog/{id}`

Поля: `name`, `selling_price`, `unit_id`, `image_id`, `is_image_deleted`, `barcode`, `ntin` (опц., строка, макс. 50), `gtin` (опц., строка, макс. 50).

> ⚠️ **Важно про `ntin`/`gtin`.** Передавайте эти поля только когда действительно хотите изменить идентичность Нацкаталога. При обычной правке (например, только цены) **не передавайте** `ntin`/`gtin` — иначе `null` затрёт идентичность Нацкаталога в Kaspi. Восстановить её синхронизацией нельзя: листинг Kaspi значение `gtin` не отдаёт.

**Код ответа зависит от позиции, а не от режима организации:** правка песочной позиции применена уже в момент ответа (`200 OK`), правка боевой позиции принята в работу (`202 Accepted`).

> ⚠️ **`202` — не подтверждение.** В бою правка доставляется в Kaspi уже после ответа, и при загруженной очереди доставка занимает больше минуты. До подтверждения у позиции сохраняются `operation=update` и всё намерение по картинке, включая новый `image_id` и её удаление. Исход проверяйте точечным `GET /catalog?ids[]=`, счётчиком `updating` в [`GET /catalog/queue`](#очередь-приёма), отказами в [`GET /catalog/errors`](#отказы-каталога) или вебхуком `catalog.item_processed`.

> ⚠️ В ответе `GET /catalog` новая цена появляется сразу, поэтому совпадение отправленного значения с ответом **не доказывает**, что правка доехала до Kaspi. Доказательство — `updating = 0` и пустой `operation` у позиции.

`PATCH` по позиции с `operation=delete` **отменяет удаление**: запрос означает «позиция мне нужна» и атомарно заменяет намерение. Отдельного отказа «снятие уже отправлено» больше нет — если снятие успело пройти, позиция будет создана заново с тем же локальным `id`.

⛔ Если позиция уже снята (`status: deleted`), `PATCH` по ней вернёт `404`: выборка идёт только по живым позициям. Заведите её заново обычным `POST /catalog` — по `external_ref` вернётся та же строка с тем же `id`; у позиции без `external_ref` появится новая строка с новым `id`, а если её штрихкод совпадает с другим живым товаром — присланная позиция сольётся с ним. Пересоздание есть только у `POST /catalog`, у `PATCH` его нет.

## Удаление товара

**Эндпоинт:** `DELETE /catalog/{id}`

**Код ответа зависит от позиции, а не от режима организации:** песочная позиция снята уже в момент ответа (`200 OK`), боевая принята в работу (`202 Accepted`) — она становится `deleting` с `operation=delete`, а после подтверждения Kaspi переходит в `deleted`.

> ⚠️ Снятие в обоих случаях **логическое**: позиция остаётся доступной чтением `GET /catalog?statuses[]=deleted` и восстанавливается повторной заливкой по тому же `external_ref` — вернётся та же позиция с тем же `id`.

> ⚠️ **Ответ приходит раньше, чем товар исчезает из кассы.** Снятие доставляется в Kaspi уже после ответа и при загруженной очереди займёт больше минуты. Проверяйте результат чтением `GET /catalog?statuses[]=deleted`, а не сразу после ответа.

После временного сбоя позиция остаётся в `deleting` — сервис вернётся к ней сам, **повторный запрос слать не нужно**. Если попытки исчерпаны, позиция читается как `failed` с сохранённым `operation=delete`, `error_code` и `failed_at` — и по-прежнему не продаётся (`sellable: false`).

**Неоднозначная торговая точка.** У одиночного удаления она больше не даёт синхронный `409`: запрос принимается с `202`, а `catalog_multi_tradepoint` появляется на самой позиции в поле `error_code`. У массового удаления этот отказ остался синхронным (`409`). Разблокировка — через поддержку.

## Массовое удаление

**Эндпоинт:** `POST /catalog/bulk-delete`

Снимает с продажи много позиций одним запросом. Метод `POST`, а не `DELETE`: тело у `DELETE` плохо поддержано HTTP-клиентами 1С.

**Лимит:** 10 запросов/мин на API-ключ.

**Ключ должен быть выпущен владельцем организации.** Ключ, привязанный к сотруднику, получает `403 catalog_delete_owner_key_required` — перевыпустите его от имени владельца. Требование есть только у массового удаления: снести каталог целиком — не рутинная операция интегратора.

### Что можно передать

Цели задаются **ровно одним списком**: `ids[]` **либо** `external_refs[]`. Оба ключа уникальны в пределах организации, поэтому одно значение — не больше одной позиции. Не больше **200** значений, превышение → `422 catalog_match_overflow`. Не задали ни одного списка либо задали оба — `422 catalog_delete_scope_required`.

> ⛔ `barcodes[]` не принимается: штрихкод не уникален, и одно значение могло бы снести сотни позиций.

> ⛔ **Режима «удали всё, чего не было в моей заливке» нет.** Сервер не может отличить оборвавшуюся выгрузку от честного сокращения каталога, поэтому список снятия строит интегратор. Поля `filter`, `sync_token` и `run_total` в операции не участвуют: лишние поля старого клиента игнорируются, но без `ids[]`/`external_refs[]` запрос ответит `422 catalog_delete_scope_required`.

Необязательные поля: `dry_run` (только посчитать и показать образец, ничего не менять и не расходовать `Idempotency-Key`) и `expected_count` (сверка с числом из разведки).

```bash
curl -X POST https://api.apipay.kz/api/v1/catalog/bulk-delete \
  -H "X-API-Key: YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: 1c-sync-2026-08-26-chunk-01" \
  -d '{"external_refs": ["1C-000123", "1C-000124"], "expected_count": 2}'
```

### Порядок полной синхронизации из 1С

1. Залейте актуальный каталог через `POST /catalog`.
2. Постройте у себя явный список ушедших позиций — `ids` либо `external_refs` — и разбейте его на чанки по **200 значений** или меньше.
3. По каждому чанку вызовите `POST /catalog/bulk-delete` с `dry_run: true` — вернётся `would_delete` (сколько позиций попадёт под удаление) и образец `sample[]`.
4. Повторите тот же запрос без `dry_run`, передав полученное `would_delete` в необязательном `expected_count` и **уникальный `Idempotency-Key` на каждый чанк**.
5. Исход смотрите по остатку в [`GET /catalog/queue`](#очередь-приёма), по строкам — точечным `GET /catalog?external_refs[]=`, по отказам — в [`GET /catalog/errors`](#отказы-каталога). Итог каждой строки дополнительно присылает вебхук `catalog.item_processed`.

Если число разошлось — `409 catalog_bulk_delete_mismatch` с полем `actual_count`: множество изменилось между разведкой и командой, **ничего не удаляется**, повторите `dry_run`. Варианта «удаляем всё равно» нет.

> ⛔ Не зеркальте удаления фильтром по времени изменения. `updated_at` не двигается у позиций, совпавших с каталогом Kaspi, и двигается у тронутых синхронизацией, поэтому отбор «удалить всё, что не менялось» снял бы живые товары и оставил мёртвые.

> ⛔ **Общего хендла у операции нет.** Ручка `GET /catalog/batches/{id}` удалена, поля `batch` и `poll_url` в ответах больше не приходят, а вебхук `catalog.batch_processed` не отправляется никогда — адрес и подпись прежние, просто тишина, по ошибке об этом не узнать. Признак «работа закончена» интегратор считает у себя по своему списку `external_ref`.

### Это фоновая операция на сутки

Позиции снимаются с продажи по одной, и во время массового удаления заливка каталога идёт медленнее. Порядок величин: 500 позиций — около двух часов, несколько тысяч — сутки с небольшим; при параллельной заливке умножьте примерно вчетверо. Планируйте окно исходя из этого, а не из времени ответа.

> ⛔ Ответ `202` — это «принято в работу», а не «удалено». Не ставьте на этот запрос HTTP-таймаут в расчёте на завершение.

> ⚠️ Позиции, попавшие в очередь снятия, перестают приниматься в корзину сразу — включая уже напечатанные листы `POST /static-qr`, где эти позиции зашиты в `cart_items`. Скан такого листа не создаст счёт, пока позиция не вернётся в продажу, а переиздать напечатанный лист нельзя. Если под удаление попадают позиции из действующих листов, верните их через `POST /catalog` либо перевыпустите листы.

### Ответы

`202` — позиции приняты в очередь снятия:

| Поле | Что значит |
|------|------------|
| `queued` | Сколько позиций поставлено в очередь снятия |
| `buried` | Сколько недоставленных призрачных строк закрыто локально |
| `already_queued[]` | Позиции, которые уже стояли в очереди удаления; их не переклеймливают. ⚠️ Список обрезан до 200 элементов — это образец, а не полный перечень |
| `already_queued_count` | Сколько позиций уже стояло в очереди, без обрезки |

`200` приходит в четырёх разных случаях — различайте их по наличию ключей:

| Ключи в теле | Что это |
|--------------|---------|
| `dry_run: true`, `would_delete`, `sample[]` | Разведка, ничего не изменено |
| `idempotent_replay: true` | Точный повтор по `Idempotency-Key`, запрос не выполнен заново |
| `queued: 0` | Удалять нечего |
| `deleted` | Песочница, удалено синхронно |

> ⚠️ В теле `dry_run` поле `already_queued` — **число** (историческая форма). В телах `queued: 0`, песочницы и в `202` это массив `id`, и рядом лежит `already_queued_count`. Тело повтора по `Idempotency-Key` состоит из `message` и `idempotent_replay` — ни того, ни другого поля в нём нет.

### Ошибки

| Код | HTTP | Значение |
|-----|------|----------|
| `catalog_not_supported` | 400 | У организации не включён каталог. Именно `400`, а не `422`: это предусловие организации, а не ошибка тела запроса |
| `catalog_delete_owner_key_required` | 403 | Ключ выпущен не владельцем организации |
| `tariff_inactive` | 403 | Тариф не активен |
| `catalog_bulk_delete_mismatch` | 409 | `expected_count` разошёлся с фактом (в теле `actual_count`) — ничего не удалено, повторите `dry_run` |
| `catalog_multi_tradepoint` | 409 | У организации несколько торговых точек, массовое удаление через API недоступно |
| `catalog_busy` | 409 | Каталог занят другой операцией, повторите через несколько секунд |
| `idempotency_key_conflict` | 409 | Ключ занят другим телом либо другой каталожной операцией, возьмите новый |
| `catalog_delete_scope_required` | 422 | Не задан ни `ids[]`, ни `external_refs[]`, либо заданы оба списка |
| `catalog_match_overflow` | 422 | Больше 200 значений в списке |

### Как вернуть позицию

Пришлите её обычным `POST /catalog` — удаление отменится. Если товар ещё не снят в Kaspi, он просто останется на месте; если снятие уже прошло, позиция заводится заново: по `external_ref` вернётся та же строка с тем же `id`, а у позиции без `external_ref`, штрихкода и НТИН в каталоге появится новая строка.

> ⛔ Возврат неоднозначен в одном случае: у позиции нет `external_ref`, а её штрихкод совпадает с другим, живым товаром — присланная позиция сольётся с ним, а приговорённая уйдёт по вашему плану. Возврат по `external_ref` однозначен всегда.

Отдельного отказа «снятие уже отправлено» больше нет: новое намерение принимается в любой момент, а при уже состоявшемся снятии позиция создаётся заново.

## Статусы товара

Словарь `status` — пять взаимоисключающих значений, и фильтр `GET /catalog?statuses[]=` принимает те же пять:

| Статус | Что значит |
|--------|------------|
| `pending` | Позиция создаётся; в каталоге Kaspi её сейчас нет |
| `active` | Позиция заведена в Kaspi и продаётся |
| `deleting` | Снятие запланировано или выполняется; продавать позицию уже нельзя |
| `deleted` | Позиция снята в Kaspi |
| `failed` | Операция над позицией брошена после исчерпания попыток; причина — в полях `error_code`/`error_message` позиции, отказы дополнительно доступны через [`GET /catalog/errors`](#отказы-каталога) |

**`status` — производное поле:** оно вычисляется из состояния позиции, а не хранится отдельно. Приоритет веток фиксирован, первое совпадение выигрывает:

```
failed → pending → deleting → deleted → active
```

Открытая операция проверяется **выше** состояния позиции. Отсюда контринтуитивный случай: снятая позиция, для которой уже открыто повторное создание, читается как `pending`, а не как `deleted` — она создаётся заново.

### Ось операции

Рядом со статусом отдаётся отдельное поле `operation` — единственное незакрытое намерение над позицией:

| Значение | Что значит |
|----------|------------|
| `null` | Незакрытых намерений нет |
| `create` | Позиция создаётся или пересоздаётся |
| `update` | Правка отправлена и ждёт подтверждения Kaspi |
| `delete` | Позиция снимается |

При отказе значение `operation` **сохраняется** вместе с `error_code`, `error_message` и `failed_at` — по нему видно, что именно не прошло. Любая позиция с `operation: delete` не принимается в корзину, даже если попытки удаления прекращены; повторный `POST /catalog` или `PATCH` заменяет намерение и возвращает позицию в работу.

### Продаваемость и каталожная идентичность

Это два **разных** факта, и одним флагом они не выражаются — выводить их из `status` не нужно, они отдаются готовыми:

| Поле | Что значит |
|------|------------|
| `sellable` | Примут ли позицию в корзину счёта, QR или подписки. `false` у снятой позиции и у позиции с открытым намерением удаления — даже если попытки прекращены |
| `in_kaspi_catalog` | Есть ли у позиции боевая идентичность номенклатуры Kaspi. При `false` счёт создастся, но позиция уедет разовой продажей, и маркировка Нацкаталога в фискальный чек по ней не проводится |

> ⚠️ **В песочнице `in_kaspi_catalog` всегда `false`** — тестовые позиции носят синтетическую идентичность номенклатуры. Это свойство тестового контура, а не предсказание для боевой позиции: маркировку проверяйте на боевой оси организации.

Позиция бывает продаваемой без каталожной идентичности и наоборот.

> ⛔ **Позицию в статусе `deleting` нельзя положить в корзину.** Причина денежная: при массовом удалении позиция стоит в этом статусе долго (порядок величин — в разделе [Массовое удаление](#массовое-удаление)), и счёт, выставленный в это окно, стал бы фискальным документом на товар, которого к моменту оплаты уже нет.
>
> Позиция восстановима — см. [Как вернуть позицию](#как-вернуть-позицию).

Форма отказа зависит от поверхности:

| Где | Что придёт |
|-----|------------|
| `POST /invoices`, `POST /invoices/qr`, `POST /static-qr` | `422`, причина — в `errors["cart_items.N.catalog_item_id"]`; отдельного `error_code` у этой ветки нет |
| `POST /invoices/bulk` | Батч по-прежнему `201`: позиция приходит в `invoices[]` как `failed` с `error_code: catalog_item_not_found`, остальные счета создаются |
| `POST /subscriptions`, `PUT /subscriptions/{id}` | `422`, тот же `errors` |
| Очередное списание по подписке | Отказа нет: списание откладывается до следующей попытки списания — счётчик неудач не растёт и подписка не уходит в льготный период |

## Очередь приёма

**Эндпоинт:** `GET /catalog/queue`

Показывает остаток вашей очереди приёма каталога. После того как агрегат партий убран, это основной способ узнать, сколько работы ещё не закрыто.

```bash
curl https://api.apipay.kz/api/v1/catalog/queue \
  -H "X-API-Key: YOUR_API_KEY"
```

Параметры: `sort_order` (`asc` — ближайшие к обработке первыми, по умолчанию; `desc`), `page`, `per_page` (20–200, по умолчанию 100).

Пагинация **плоская** — поля лежат в корне ответа, без обёртки `meta`:

| Поле | Что значит |
|------|------------|
| `data[]` | Строки очереди **создания**: `id`, `external_ref`, `name`, `queued_at` |
| `total` | Сколько позиций ждут создания |
| `updating` | Сколько существующих позиций ждут подтверждения правки в Kaspi (`operation: update`) |
| `deleting` | Сколько позиций ждут снятия в Kaspi |
| `queue` | Сводка состояния: `state` и `eta_minutes` |

Три счётчика считаются отдельно. Без `updating` и `deleting` ответ выглядел бы «очередь пуста», пока тысячи позиций ждут правки или снятия.

`queue.state` объясняет, почему очередь может не двигаться:

| Значение | Что значит |
|----------|------------|
| `draining` | Очередь двигается |
| `paused_throttle` | Пауза из-за ограничения частоты со стороны Kaspi; секунды до продолжения — в `throttle_retry_in_seconds` |
| `paused_hold` | Пауза-накопление |
| `not_connected` | У организации не подключён кассир |
| `sandbox` | Организация в тестовом режиме |

`queue.eta_minutes` — целое число только при `state: draining` и непустой очереди, иначе `null`.

**Лимит:** 600 запросов/мин на ключ, общий лимит запросов при этом не расходуется.

## Отказы каталога

**Эндпоинт:** `GET /catalog/errors`

Отказавшие операции каталога вашей организации. Вместе с `GET /catalog/queue` это единственный способ узнать исход массовой работы, если вы не принимаете вебхуки.

```bash
curl "https://api.apipay.kz/api/v1/catalog/errors?from=2026-08-26" \
  -H "X-API-Key: YOUR_API_KEY"
```

Параметры: `from`, `to` — окно по **моменту отказа** (`failed_at`); без `from` берутся последние 7 дней. Минуты и секунды опциональны (`2026-08-26`, `2026-08-26 10`, `2026-08-26 10:30`). Голая дата и дата-время без смещения трактуются в Asia/Almaty (+05:00) — это календарный день продавца; явное смещение берётся как есть. Голая дата в `to` включает весь день целиком, а дата-время означает ровно этот момент: `10` — это `10:00:00`, а не конец часа. `to` должен быть не раньше `from`, иначе `422`. Ещё есть `sort_order` (по умолчанию `desc`), `page`, `per_page` (20–200, по умолчанию 100).

Пагинация тоже плоская: `current_page`, `data[]`, `total`. Поля строки: `id`, `external_ref`, `name`, `barcode`, `ntin`, `operation` (что именно отказало), `error_code`, `error_message`, `queued_at`, `failed_at`.

Тексты `error_message` обезличены — сырые ответы Kaspi не отдаются.

> ⛔ Фильтр `batch_id` здесь тоже удалён и **отклоняется явно**: `422 catalog_batch_filter_removed`. Отбирайте свои позиции окном `from`/`to` и собственным списком `external_ref`.

**Лимит:** 600 запросов/мин на ключ, общий лимит запросов при этом не расходуется.

## Использование с корзиной

```bash
curl -X POST https://api.apipay.kz/api/v1/invoices \
  -H "X-API-Key: YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "phone_number": "87001234567",
    "cart_items": [
      {"catalog_item_id": 101, "count": 2}
    ]
  }'
```

## Примеры кода

### JavaScript

```javascript
// ⚠️ X-API-Key — секрет. Все вызовы API выполняйте со своего сервера;
// в код, который попадает в браузер, ключ помещать нельзя.
import fs from 'node:fs/promises'

const formData = new FormData()
formData.append('image', new Blob([await fs.readFile('photo.jpg')]), 'photo.jpg')
const upload = await fetch('https://api.apipay.kz/api/v1/catalog/upload-image', {
  method: 'POST', headers: { 'X-API-Key': process.env.APIPAY_KEY }, body: formData
})
const { image_id } = await upload.json()

await fetch('https://api.apipay.kz/api/v1/catalog', {
  method: 'POST',
  headers: { 'X-API-Key': process.env.APIPAY_KEY, 'Content-Type': 'application/json' },
  body: JSON.stringify({ items: [{ name: 'Кофе латте', selling_price: 1500, unit_id: 1, image_id }] })
})
```

### Python

```python
import requests
# Загрузка изображения
with open('photo.jpg', 'rb') as f:
    resp = requests.post('https://api.apipay.kz/api/v1/catalog/upload-image',
        headers={'X-API-Key': 'YOUR_API_KEY'}, files={'image': f})
image_id = resp.json()['image_id']

# Создание товаров
requests.post('https://api.apipay.kz/api/v1/catalog',
    headers={'X-API-Key': 'YOUR_API_KEY', 'Content-Type': 'application/json'},
    json={'items': [{'name': 'Кофе латте', 'selling_price': 1500, 'unit_id': 1, 'image_id': image_id}]})
```
