# Каталог

API каталога позволяет управлять товарами. Товары из каталога используются при создании счетов с корзиной (`cart_items`).

## Единицы измерения

**Эндпоинт:** `GET /catalog/units`

Возвращает доступные единицы измерения для товаров каталога.

```bash
curl https://api.apipay.kz/api/v1/catalog/units \
  -H "X-API-Key: YOUR_API_KEY"
```

Ответ: `{ "data": [{ "id": 1, "name": "шт", "name_kaz": "дана" }, ...] }`

## Список товаров

**Эндпоинт:** `GET /catalog`

Фильтры: `search`, `barcode`, `first_char`, `statuses[]` (можно несколько значений: `active`, `pending`, `deleting`, `deleted`, `failed`), `without_ntin`. Пагинация: `page`, `per_page` (1-200).

> ⚠️ **Без `statuses[]` отдаются только `active`.** Чтобы увидеть позиции в других статусах, перечислите их явно: `?statuses[]=active&statuses[]=deleted`. Так же проверяют, что удаление доехало до Kaspi.

**Точечное чтение.** Параметры `ids[]`, `external_refs[]`, `barcodes[]`, `ntins[]` возвращают конкретные позиции в любых статусах и без пагинации — форма `{"data": [...]}`. Ограничений два: суммарно не больше 200 значений по всем четырём наборам и не больше 1000 найденных строк соответствий. Превышение любого отдаёт `422` с `error_code: catalog_match_overflow` — разбейте запрос на части. Это штатный способ подтвердить результат заливки или удаления по своим кодам 1С.

Фильтр `without_ntin=true` возвращает только позиции без НТИН (`ntin` = `null`), независимо от наличия штрихкода — шире, чем поле ответа `ntin_missing` (оно требует непустой `barcode`). Удобно оценивать остаток «сколько позиций осталось доделать» по `meta.total`. Компонуется со всеми режимами и фильтрами.

Каждый товар в ответе содержит поле `created_at` — дата создания в системе (ISO 8601). Доступно сразу после создания, даже если Kaspi ещё не вернул `date_added`.

Каждый товар также содержит поле `gtin` (строка или `null`) — GTIN из Нацкаталога, если товар был создан с ним. Листинг Kaspi значение `gtin` не возвращает, поэтому синхронизация каталога его не затирает.

## Загрузка изображения

**Эндпоинт:** `POST /catalog/upload-image`

```bash
curl -X POST https://api.apipay.kz/api/v1/catalog/upload-image \
  -H "X-API-Key: YOUR_API_KEY" \
  -F "image=@photo.jpg"
```

Формат: `multipart/form-data`. Только JPEG и PNG, макс. 6 МБ, стороны 64…6000 px, площадь до 12 Мпикс. Файлы gif, webp, bmp и svg отклоняются (`422 invalid_file_type`) — конвертируйте их на своей стороне. Файл больше 6 МБ — `413 file_too_large`. Лимит: 60 запросов в минуту и 2000 в сутки на ключ.

Ответ: `{"image_id": "550e8400-..."}`.

## Сканирование штрихкода (Нацкаталог)

**Эндпоинт:** `POST /catalog/scan`

Резолвит штрихкод в Нацкаталоге Kaspi и возвращает карточки товаров-кандидатов. Используйте перед созданием товара, чтобы подтянуть официальное название, НТИН и GTIN. Работает синхронно.

```bash
curl -X POST https://api.apipay.kz/api/v1/catalog/scan \
  -H "X-API-Key: YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"input": "4607015232646"}'
```

Поле: `input` (обяз., строка, макс. 64) — штрихкод, введённый вручную или полученный со сканера.

Ответ `200 OK`:

```json
{
  "data": [
    {
      "id": 1118196,
      "name": "ВАФЛИ ЯШКИНО ОРЕХОВЫЕ 300Г",
      "ntin": "0200009461097",
      "gtin": "4607015232646",
      "barcode": "4607015232646",
      "unit_id": null,
      "image_link": null
    }
  ],
  "normalized_barcode": "4607015232646",
  "scan_result": { "code": "ok", "message": null }
}
```

Один штрихкод может вернуть несколько кандидатов (общий `gtin`, разные `ntin`) — окончательный выбор делает продавец. Поля кандидата (`id`, `name`, `ntin`, `gtin`, `barcode`, `unit_id`, `image_link`) затем передаются в создание товара.

Если товар не найден — приходит `data: []` и/или `scan_result.code` отличный от `"ok"`. Это **не ошибка**: HTTP по-прежнему `200`. В этом случае создавайте товар обычным путём, без `ntin`/`gtin`.

**Ошибки:**

| Код | Значение | Что делать |
|-----|----------|------------|
| `422` | `input` пустой или длиннее 64 символов | Исправьте ввод |
| `400` `kaspi_session_expired` | Сессия Kaspi истекла | Переподключите кассира Kaspi, затем повторите |
| `429` `kaspi_throttled` | Слишком часто (в теле `retry_after_seconds`, в заголовке `Retry-After`) | Подождите указанное время и повторите |
| `503` `kaspi_scan_unavailable` | Нацкаталог временно недоступен | Повторите позже |

**Лимиты:** 30 запросов/мин и 2000/сутки на API-ключ. Если Kaspi ограничил частоту, эндпоинт отвечает `429 kaspi_throttled` — дождитесь времени из `retry_after_seconds` (заголовок `Retry-After`) и повторите.

**Типовой сценарий:** сканирование штрихкода → `POST /catalog/scan` → показать `data[]` (если пусто — создать товар без `ntin`/`gtin`) → продавец выбирает кандидата → `POST /catalog` с `ntin`/`gtin`/`from_catalog: true` → товар создаётся в статусе `pending` → асинхронно уходит в Kaspi → `active`.

## Создание товаров

**Эндпоинт:** `POST /catalog`

Пакетное создание: 1–100 позиций за запрос.

```bash
curl -X POST https://api.apipay.kz/api/v1/catalog \
  -H "X-API-Key: YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"items": [{"name": "Кофе латте", "selling_price": 1500, "unit_id": 1, "image_id": "550e8400-..."}]}'
```

Поля: `name` (обяз., строка, макс. 255), `selling_price` (обяз., число, мин. 0.01), `unit_id` (обяз., целое), `image_id` (опц., UUID из `POST /catalog/upload-image`), `barcode` (опц., строка, макс. 32), `external_ref` (опц., строка, макс. 191) — ваша ссылка на позицию, например код номенклатуры 1С.

Поля Нацкаталога (опц., заполняются из выбранного кандидата `POST /catalog/scan`):

- `ntin` (строка, макс. 50) — НТИН выбранного кандидата.
- `gtin` (строка, макс. 50) — GTIN, только для кандидатов GS1.
- `from_catalog` (bool, по умолчанию `false`) — признак, что товар создан из Нацкаталога.

Пример элемента с данными Нацкаталога: `{"name": "ВАФЛИ ЯШКИНО ОРЕХОВЫЕ 300Г", "selling_price": 450, "unit_id": 1, "barcode": "4607015232646", "ntin": "0200009461097", "gtin": "4607015232646", "from_catalog": true}`.

**Используйте `external_ref` как ключ маппинга**, а не штрихкод и не имя: на один штрихкод у продавца может быть несколько товаров. По `external_ref` позиция потом читается точечно (`?external_refs[]=`), обновляется повторной заливкой `POST /catalog` и возвращается из очереди удаления. В `PATCH /catalog/{id}` поле `external_ref` не принимается — точечная правка идёт по `id`.

**Повторная заливка не создаёт дублей.** Если позиция совпала с уже существующим товаром, возвращается его живой `id` с маркером `matched_existing: true`. Совпадение ищется сначала по `external_ref`, затем по штрихкоду или НТИН вместе с именем. Если штрихкод совпал, а имя другое, позиция матчится без перезаписи имени и цены — маркер `name_differs: true`, имя правьте явным `PATCH /catalog/{id}`. `external_ref` существующего товара не перетирается никогда.

**Битая позиция не роняет запрос.** Каждая позиция валидируется отдельно: валидные уходят в `data[]`, отклонённые — в `rejected[]`. Ключ `rejected[]` присутствует в ответе всегда, в том числе пустым. `422` остаётся только за структурными ошибками самого запроса: `items` отсутствует, не массив, пуст или длиннее 100 позиций.

**Заголовок `Idempotency-Key`** (или поле `idempotency_key`, макс. 191 символ) — повтор с тем же ключом возвращает существующий батч (`200`), не создавая позиции заново.

> ⚠️ Пространство ключей идемпотентности **общее** с массовым удалением. Ключ, уже занятый операцией другого типа, отдаёт `409 idempotency_key_conflict` — возьмите новый, повторять с тем же бесполезно.

**Метка прогона `sync_token`** (опц., макс. 64 символа, алфавит `[A-Za-z0-9._:-]`) проставляется на каждую упомянутую позицию — включая те, по которым работы не было, потому что они совпали с каталогом Kaspi. Метка нужна, чтобы потом снять остаток «всё, чего в этой заливке не было», — см. [Массовое удаление](#массовое-удаление). Все запросы одного прогона шлют один и тот же токен. Повтор с тем же ключом идемпотентности токен не обновляет, поэтому точку отсчёта берите до первого запроса прогона.

**Код ответа:** `202 Accepted` (production, позиции в статусе `pending`) / `201 Created` (sandbox, позиция активна сразу). В ответе — `data[]`, `rejected[]` и объект `batch`; у товара присутствует поле `gtin`.

## Обновление товара

**Эндпоинт:** `PATCH /catalog/{id}`

Поля: `name`, `selling_price`, `unit_id`, `image_id`, `is_image_deleted`, `barcode`, `ntin` (опц., строка, макс. 50), `gtin` (опц., строка, макс. 50).

> ⚠️ **Важно про `ntin`/`gtin`.** Передавайте эти поля только когда действительно хотите изменить идентичность Нацкаталога. При обычной правке (например, только цены) **не передавайте** `ntin`/`gtin` — иначе `null` затрёт идентичность Нацкаталога в Kaspi. Восстановить её синхронизацией нельзя: листинг Kaspi значение `gtin` не отдаёт.

**Код ответа:** `200 OK` (sandbox) / `202 Accepted` (production).

`PATCH` по позиции, стоящей в очереди на удаление, **отменяет удаление** — позиция возвращается в работу. Исключение — узкое окно, когда снятие уже отправлено в Kaspi: тогда приходит `409 catalog_delete_in_progress`. Повторите через несколько секунд. Если позиция к этому моменту уже снята, `PATCH` по ней вернёт `404` — заведите её заново обычным `POST /catalog` с тем же `external_ref`: вернётся та же строка с тем же `id`.

Поле `sync_token` принимается и здесь. Оно нужно, если позицию вы ведёте только через `PATCH`: без метки она считается неупомянутой в прогоне и попадёт под удаление остатка. Метка проставляется независимо от того, менялись ли поля.

## Удаление товара

**Эндпоинт:** `DELETE /catalog/{id}`

**Код ответа:** `200 OK` (sandbox, позиция удаляется сразу) / `202 Accepted` (production).

В рабочем режиме позиция переходит в статус `deleting`, а с продажи в Kaspi её снимает фоновая обработка.

> ⚠️ **Ответ приходит раньше, чем товар исчезает из кассы.** Обычно это считаные секунды, но если параллельно идёт массовая операция с каталогом, очередь загружена и снятие займёт дольше. Проверяйте результат чтением `GET /catalog?statuses[]=deleted`, а не сразу после ответа.

Сбой при снятии не переводит позицию в `failed`: она остаётся в `deleting`, пока не снимется, — сервис вернётся к ней сам. **Повторный запрос слать не нужно.** Практическое следствие: `failed` у удалений вы будете видеть редко, а `deleting` — дольше.

**Ошибка:** `409 catalog_multi_tradepoint` — у организации несколько торговых точек, и удаление каталога через API для неё недоступно. Состояние позиции при этом не меняется. Разблокировка — через поддержку.

## Массовое удаление

**Эндпоинт:** `POST /catalog/bulk-delete`

Снимает с продажи много позиций одним запросом. Метод `POST`, а не `DELETE`: тело у `DELETE` плохо поддержано HTTP-клиентами 1С.

**Лимит:** 10 запросов/мин на API-ключ.

**Ключ должен быть выпущен владельцем организации.** Ключ, привязанный к сотруднику, получает `403 catalog_delete_owner_key_required` — перевыпустите его от имени владельца. Требование есть только у массового удаления: снести каталог целиком — не рутинная операция интегратора.

### Два режима

Задайте ровно один, иначе придёт `422 catalog_delete_scope_required`.

**Список** — `ids[]` **либо** `external_refs[]`. Оба ключа уникальны в пределах организации, поэтому одно значение — не больше одной позиции. Не больше 200 значений, превышение → `422 catalog_match_overflow`. Наборы взаимоисключающие и между собой: пришлёте оба — придёт тот же `422 catalog_delete_scope_required` с `reason: mode_required`.

> ⛔ `barcodes[]` не принимается: штрихкод не уникален, и одно значение могло бы снести сотни позиций. Штрихкоды — только через фильтр, где есть `dry_run`.

**Фильтр** — `filter.sync_token_not`: «удали всё, чего не было в моей заливке». Обязателен `expected_count`: множество большое и необратимое. Капом в 200 режим фильтра не ограничен и снимает весь подходящий остаток одним запросом.

```bash
curl -X POST https://api.apipay.kz/api/v1/catalog/bulk-delete \
  -H "X-API-Key: YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"filter": {"sync_token_not": "run-2026-08-13-a"}, "expected_count": 6870}'
```

### Порядок полной синхронизации из 1С

1. Залейте актуальный каталог через `POST /catalog`, передавая один и тот же `sync_token` во всех запросах прогона.
2. Вызовите `POST /catalog/bulk-delete` с `dry_run: true` — узнаете, сколько позиций попадёт под удаление, и увидите образец.
3. Повторите тот же запрос без `dry_run`, передав полученное число в `expected_count`.
4. Дождитесь вебхука `catalog.batch_processed` с `kind: delete` либо опрашивайте `poll_url`.

Если число разошлось — `409 catalog_bulk_delete_mismatch` с полем `actual_count`: каталог изменился между разведкой и командой, повторите `dry_run`. Варианта «удаляем всё равно» нет.

> ⛔ Не зеркальте удаления фильтром по времени изменения. `updated_at` не двигается у позиций, совпавших с каталогом Kaspi, и двигается у тронутых синхронизацией, поэтому отбор «удалить всё, что не менялось» снял бы живые товары и оставил мёртвые.

### Что попадает под фильтр

Под `filter.sync_token_not` попадают только позиции, помеченные **другим** `sync_token`. Позиция без метки вовсе — заведённая в кассе вручную, пришедшая из каталога Kaspi, залитая до того, как вы начали передавать `sync_token`, — остатком не считается и под удаление не идёт.

Если снимать нужно и такие, передайте `filter.include_never_stamped: true`. Это не разовая процедура первого прогона: непомеченные позиции появляются постоянно, пока каталогом пользуются из кассы.

**Прогон обязан быть полным.** Если меткой помечена слишком малая доля живого каталога, удаление отбивается `422 catalog_delete_filter_invalid` с `reason: coverage_too_low` и числами `stamped` (сколько позиций помечено) и `visible` (сколько живых всего). Так отсекается оборвавшаяся выгрузка: у позиций, до которых заливка не дошла, лежит метка прошлого прогона — она не пустая и не равна текущей, то есть под фильтр ушёл бы весь остаток каталога. Лечится повторной полной заливкой, а не подгонкой `expected_count`.

Если этой меткой не помечено вообще ничего, придёт `reason: token_never_used` — проверьте, тот ли токен вы передали.

> ⚠️ **Список значений `reason` открытый** — неизвестное значение обрабатывайте общей веткой. У `catalog_delete_scope_required` значения свои: `mode_required` (не задан ни один режим либо задано несколько) и `expected_count_required`.

### Это фоновая операция на сутки

Позиции снимаются с продажи по одной, и во время массового удаления заливка каталога идёт медленнее — обе операции работают в одной очереди. Порядок величин: 500 позиций — около двух часов, несколько тысяч — сутки с небольшим; при параллельной заливке умножьте примерно вчетверо. Планируйте окно исходя из этого, а не из времени ответа.

> ⛔ Ответ `202` — это «принято в работу», а не «удалено». Не ставьте на этот запрос HTTP-таймаут в расчёте на завершение.

### Ответы

`202` — позиции приняты в очередь: `batch`, `queued`, `already_queued[]` (позиции, которые уже стояли в очереди удаления; их не переклеймливают) и `already_queued_count`.

`200` приходит в четырёх разных случаях — различайте их по наличию ключей:

| Ключи в теле | Что это |
|--------------|---------|
| `dry_run: true`, `would_delete`, `sample[]` | Разведка, ничего не изменено |
| `batch` без `queued` | Повтор по `Idempotency-Key`, отдан существующий батч |
| `queued: 0` | Удалять нечего |
| `deleted` | Песочница, удалено синхронно |

> ⚠️ В теле `dry_run` поле `already_queued` — **число** (историческая форма). В телах `queued: 0`, песочницы и в `202` это массив `id`, и рядом лежит `already_queued_count`. Повтор по `Idempotency-Key` состоит из одного `batch` — ни того, ни другого поля в нём нет.

### Ошибки

| Код | HTTP | Значение |
|-----|------|----------|
| `catalog_not_supported` | 400 | У организации не включён каталог. Именно `400`, а не `422`: это предусловие организации, а не ошибка тела запроса |
| `catalog_delete_owner_key_required` | 403 | Ключ выпущен не владельцем организации |
| `tariff_inactive` | 403 | Тариф не активен |
| `catalog_bulk_delete_mismatch` | 409 | `expected_count` разошёлся с фактом (в теле `actual_count`) — повторите `dry_run` |
| `catalog_multi_tradepoint` | 409 | У организации несколько торговых точек, удаление через API недоступно |
| `catalog_busy` | 409 | Каталог занят другой операцией, повторите через несколько секунд |
| `idempotency_key_conflict` | 409 | Ключ занят операцией другого типа, возьмите новый |
| `catalog_delete_scope_required` | 422 | Уточнение в `reason`: `mode_required` или `expected_count_required` |
| `catalog_delete_filter_invalid` | 422 | Уточнение в `reason`: `token_never_used` или `coverage_too_low` |
| `catalog_match_overflow` | 422 | Слишком много значений в списке |

### Как вернуть позицию

Пришлите её обычным `POST /catalog` — удаление отменится. Если товар ещё не снят в Kaspi, он просто останется на месте; если снятие уже прошло, позиция заводится заново: по `external_ref` вернётся та же строка с тем же `id`, а у позиции без `external_ref`, штрихкода и НТИН в каталоге появится новая строка.

> ⛔ Два случая, когда возврат не сработает:
>
> 1. у позиции нет `external_ref`, а её штрихкод совпадает с другим, живым товаром — присланная позиция сольётся с ним, а приговорённая уйдёт по вашему плану. Возврат по `external_ref` однозначен всегда;
> 2. удаление именно этой позиции уже отправлено в Kaspi — придёт `catalog_delete_in_progress` (в `rejected[]` у `POST /catalog`, `409` у `PATCH /catalog/{id}`). Повторите через несколько секунд: если позиция снялась, она будет заведена заново.

## Статусы товара

| Статус | Что значит |
|--------|------------|
| `pending` | Позиция создана у нас и ждёт отправки в Kaspi |
| `active` | Позиция заведена в Kaspi и продаётся |
| `deleting` | Позиция снимается с продажи; в Kaspi её ещё видно |
| `deleted` | Позиция снята в Kaspi |
| `failed` | Kaspi отклонил позицию; причина — в `GET /catalog/errors` |

> ⛔ **Позицию в статусе `deleting` нельзя положить в корзину.** Отказ `422` приходит на всех платёжных поверхностях: `POST /invoices`, `POST /invoices/bulk`, `POST /invoices/qr`, печатный QR, повторяющиеся счета и биллинг подписок. Причина денежная: снятие позиции из кассы идёт сутками, и счёт, выставленный в это окно, стал бы фискальным документом на товар, которого к моменту оплаты уже нет.
>
> Позиция восстановима — см. [Как вернуть позицию](#как-вернуть-позицию). У подписок очередное списание в этой ситуации не проваливается, а откладывается до следующего прогона: попытки не сгорают и подписка не уходит в льготный период.

Очередь приёма и очередь снятия считаются отдельно: `GET /catalog/queue` отдаёт счётчик `deleting` — сколько позиций ждут снятия в Kaspi.

## Использование с корзиной

```bash
curl -X POST https://api.apipay.kz/api/v1/invoices \
  -H "X-API-Key: YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "phone_number": "87001234567",
    "cart_items": [
      {"catalog_item_id": 101, "count": 2}
    ]
  }'
```

Подробнее: [Счета](invoices.md).

## Примеры кода

### JavaScript

```javascript
// ⚠️ X-API-Key — секрет. Все вызовы API выполняйте со своего сервера;
// в код, который попадает в браузер, ключ помещать нельзя.
import fs from 'node:fs/promises'

const formData = new FormData()
formData.append('image', new Blob([await fs.readFile('photo.jpg')]), 'photo.jpg')
const upload = await fetch('https://api.apipay.kz/api/v1/catalog/upload-image', {
  method: 'POST', headers: { 'X-API-Key': process.env.APIPAY_KEY }, body: formData
})
const { image_id } = await upload.json()

await fetch('https://api.apipay.kz/api/v1/catalog', {
  method: 'POST',
  headers: { 'X-API-Key': process.env.APIPAY_KEY, 'Content-Type': 'application/json' },
  body: JSON.stringify({ items: [{ name: 'Кофе латте', selling_price: 1500, unit_id: 1, image_id }] })
})
```

### Python

```python
import requests
# Загрузка изображения
with open('photo.jpg', 'rb') as f:
    resp = requests.post('https://api.apipay.kz/api/v1/catalog/upload-image',
        headers={'X-API-Key': 'YOUR_API_KEY'}, files={'image': f})
image_id = resp.json()['image_id']

# Создание товаров
requests.post('https://api.apipay.kz/api/v1/catalog',
    headers={'X-API-Key': 'YOUR_API_KEY', 'Content-Type': 'application/json'},
    json={'items': [{'name': 'Кофе латте', 'selling_price': 1500, 'unit_id': 1, 'image_id': image_id}]})
```
