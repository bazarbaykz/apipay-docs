# Partner API

Partner API позволяет платформам и CRM-системам подключать своих клиентов
к ApiPay и выставлять счета от их имени — без ручного создания аккаунтов.

> **Для кого это:** интеграторы (CRM-системы, маркетплейсы, платформы),
> которые подключают мерчантов программно. Если вам нужно просто принимать
> платежи для своего бизнеса — используйте обычный [API](getting-started.md).

## Аутентификация

Все запросы Partner API используют заголовок `X-Partner-Key`:

```
X-Partner-Key: pk_your_partner_key_here
```

Партнёрский ключ выдаётся командой ApiPay после одобрения заявки на
партнёрство. Он показывается только один раз при выдаче и хранится в виде
хеша — сохраните его надёжно, восстановить ключ невозможно.

| Параметр | Значение |
|----------|----------|
| Base URL | `https://api.apipay.kz` |
| Аутентификация | Заголовок `X-Partner-Key: pk_...` |
| Content-Type | `application/json` |

## Поток онбординга мерчанта

Главный сценарий — подключить мерчанта в ApiPay программно. Авторизация
кассира завершается кодом, который Kaspi присылает по SMS на номер кассира.
Код вводит сам мерчант — в вашей форме онбординга; передайте его в
`verify-otp` и не сохраняйте у себя.

| Шаг | Запрос | Назначение |
|-----|--------|------------|
| 1 | `POST /api/partner/organizations` | Создать организацию мерчанта |
| 2 | `POST /api/partner/organizations/{id}/kaspi-auth/init` | Начать авторизацию кассира |
| 3 | `POST /api/partner/organizations/{id}/kaspi-auth/send-phone` | Kaspi отправляет SMS кассиру |
| 4 | `POST /api/partner/organizations/{id}/kaspi-auth/verify-otp` | Подтвердить код из SMS |
| 5 | `POST /api/partner/organizations/{id}/api-key` | Выдать API-ключ мерчанта + webhook |

> **Важно:** идентификатор авторизации `process_id` живёт 10 минут.
> Шаги 3 и 4 нужно выполнить в этом окне.

Готовые примеры онбординга — в [examples/](../../examples/):
`javascript/partner-onboarding.js`, `python/partner_onboarding.py`,
`php/partner-onboarding.php`, `curl/partner-onboarding.sh`.

## Эндпоинты

### POST /api/partner/organizations

Создать организацию мерчанта. Идемпотентно по `external_id` — повторный
запрос вернёт существующую организацию.

| Параметр | Тип | Обязательный | Описание |
|----------|-----|--------------|----------|
| `has_catalog` | boolean | Нет | Создать организацию с каталогом товаров |
| `external_id` | string | Нет | Ваш идентификатор клиента в CRM |

**Ответ** `201 Created` (или `200 OK` при идемпотентном повторе):

```json
{ "success": true, "organization": { ... } }
```

### GET /api/partner/organizations

Список ваших организаций с пагинацией.

| Параметр | Тип | Обязательный | Описание |
|----------|-----|--------------|----------|
| `per_page` | number | Нет | Размер страницы: 1–100 (по умолчанию 25) |
| `page` | number | Нет | Номер страницы (по умолчанию 1) |

**Ответ:**

```json
{
  "success": true,
  "organizations": [ ... ],
  "current_page": 1,
  "per_page": 25,
  "total": 42,
  "last_page": 2
}
```

### GET /api/partner/organizations/{id}

Получить карточку организации.

**Ответ:** `{ "success": true, "organization": { ... } }`

### DELETE /api/partner/organizations/{id}

Отвязать организацию: деактивирует её API-ключи и помечает как удалённую.

**Ответ:** `{ "success": true }`

### POST /api/partner/organizations/{id}/kaspi-auth/init

Шаг 1 онбординга — начать авторизацию кассира Kaspi.

**Ответ:** `{ "success": true, "process_id": "..." }` — `process_id` живёт 10 минут.

### POST /api/partner/organizations/{id}/kaspi-auth/send-phone

Шаг 2 онбординга — Kaspi отправляет SMS-код на телефон кассира.

| Параметр | Тип | Обязательный | Описание |
|----------|-----|--------------|----------|
| `cashier_phone` | string | Да | Номер кассира в формате `7XXXXXXXXXX` |

**Ответ:** `{ "success": true }`.
Возможные ошибки: `invalid_phone` (422), `not_cashier` (422), `no_process` (409), `sms_failed` (502).

### POST /api/partner/organizations/{id}/kaspi-auth/verify-otp

Шаг 3 онбординга — подтвердить код из SMS.

| Параметр | Тип | Обязательный | Описание |
|----------|-----|--------------|----------|
| `otp` | string | Да | Код из SMS, 4–6 цифр |

**Ответ** при успехе: `{ "success": true, "mode": "self", "organization": { ... } }`.
При неверном коде: `{ "success": false, "error": "invalid_otp" }`.

**Личность организации Kaspi.** Пара «БИН + идентификатор организации в Kaspi» закрепляется при первой привязке и дальше не меняется. Подключение кассира само по себе владельца **не переносит**:

| Код | HTTP | Что значит |
|-----|------|------------|
| `organization_identity_conflict` | 409 | Организация Kaspi не совпала с закреплённой либо эта пара уже занята другой организацией. Ответ намеренно не раскрывает реквизиты чужой организации. Если владелец бизнеса действительно сменился, обращение идёт в поддержку 77003076512 |
| `organization_identity_unavailable` | 502 | Kaspi не вернул достоверные данные. Привязка не блокируется, и ранее подтверждённая пара сохраняется: попытка входа просто завершается, повтор — с нового запроса кода |

Другие терминальные исходы этого шага: `context_expired` (409, Kaspi потерял контекст — нужен новый `init`, а не повтор OTP), `no_process` (409), `cashier_unavailable` (409), `not_registered` (422, номер не заведён кассиром — сессия закрыта, повтор бессмыслен).

### GET /api/partner/organizations/{id}/kaspi-auth/status

Статус авторизации кассира.

**Ответ:** `{ "success": true, "status": "pending|active|...", "process_status": "...", "attempt_status": "none", "kaspi_connected": true, "expires_at": "..." }`

Поле `attempt_status` — статус отдельной попытки авторизации. Это всегда строка; когда попытки нет — `none`. Значения контрактом не фиксированы: ветвитесь по `status` и `process_status`, а не по нему. Рабочая сессия в начале переавторизации не очищается, поэтому `status` и `attempt_status` читаются раздельно.

### POST /api/partner/organizations/{id}/api-key

Создать или перевыпустить `X-API-Key` мерчанта и webhook. Идемпотентно.

| Параметр | Тип | Обязательный | Описание |
|----------|-----|--------------|----------|
| `name` | string | Нет | Название ключа |
| `webhook_url` | string | Да | URL для webhook-уведомлений (приватные и внутренние адреса отклоняются) |
| `webhook_secret` | string | Нет | Секрет для подписи webhook (генерируется автоматически, если не указан) |

**Ответ:**

```json
{
  "success": true,
  "key": "<plaintext, показывается один раз>",
  "key_id": 200,
  "webhook_url": "https://your-crm.example.com/webhooks/kaspi",
  "webhook_secret": "<plaintext>",
  "is_org_default": true,
  "regenerated": false
}
```

`key` показывается только один раз — сохраните его надёжно. Используйте его
как `X-API-Key` для обычного API, чтобы работать от имени мерчанта.


## Тарифы мерчантов

Подписка мерчанта на ApiPay оформляется партнёром. Все пути ниже — относительно `https://api.apipay.kz/api/partner`, аутентификация — тем же `X-Partner-Key`.

### Два режима выдачи тарифа

| Режим | Что делает партнёр |
|-------|--------------------|
| `payment` (по умолчанию) | Платит за тариф мерчанта — счётом через Kaspi (`.../tariff/pay`) либо счётом на юрлицо (`.../tariff/invoice`) |
| `assignment` | Назначает тариф бесплатно (`.../tariff/assign`), а с ApiPay рассчитывается по договору отдельно |

Режим назначает ApiPay, сменить его через API нельзя. Отдельным полем по ключу `X-Partner-Key` он не отдаётся: партнёр в режиме `payment`, вызвавший назначение, получает `403 assignment_not_enabled`.

Свою сетку лимитов вы видите в каталоге тарифов — `GET /tariff-plans` отдаёт `tiers[].daily_limit`, `tiers[].label` и `tiers[].limits_source`.

### GET /tariff-plans

Каталог тарифов: 4 тарифа (`start`, `business`, `pro`, `pro_max`) и 12 планов — тариф × период 1/3/6 месяцев со скидками за длинный период.

Каталог отдаётся **глазами вашего партнёрского аккаунта**. Если ApiPay назначил вам сетку лимитов (white-label), в `tiers[].daily_limit` и `tiers[].label` приходят ваши значения, а `tiers[].limits_source` показывает источник: `partner_grid` — сетка, `config` — глобальный каталог. **Цены сетка не меняет никогда**: `base_price` и `plans[].price` всегда глобальные. Чужая сетка не отдаётся ни при каких условиях.

Суточные лимиты глобального каталога: Start — до 30 счетов, Business — до 100, Pro — до 300, Pro Max — до 600.

### GET /organizations/{id}/tariff

Снимок подписки мерчанта. Отсутствие тарифа — это `status: "none"`, а не `404`. Поле `next_payment.amount` приходит всегда.

Поля индивидуальных условий: `is_custom` (`true` — у мерчанта договорные условия), `tier_label` (имя тарифа так, как оно продано этому мерчанту) и `daily_limit`.

> ⚠️ При `is_custom: true` поле `tier` остаётся **обычным** идентификатором (`pro`) — значения `custom` не существует. Витринное имя показывайте из `tier_label`, а ветвление стройте по `tier`.

### POST /organizations/{id}/tariff/pay

Оплата тарифа мерчанта счётом через Kaspi. Тело: `tier_id`, `period_months`, `phone` (телефон **плательщика**, формат `8XXXXXXXXXX`, не кассира), опционально `set_billing_phone`.

Тариф активируется асинхронно после оплаты — ждите вебхук `invoice.status_changed` со статусом `paid`. Триал сохраняется: оплата продлевает подписку от конца триала или текущего периода. Тестовая организация активируется мгновенно: `201`, `payment.status: "completed"`, `self_api_invoice_id: null`.

Апгрейда эта ручка не знает — здесь всегда полная цена плана.

### POST /organizations/{id}/tariff/assign

Бесплатное назначение тарифа мерчанту в режиме `assignment`. Тело: `tier_id`, `period_months`. Тариф активируется **синхронно** — счёта в Kaspi нет, телефон плательщика не нужен.

- `201` — тариф назначен, срок продлён, `already_assigned: false`.
- `200` — запрошенный горизонт уже покрыт назначением того же тарифа: срок не продлевается, второго платежа не создаётся, `already_assigned: true`. Идемпотентность считается **покрытием** (дата истечения не раньше запрошенного горизонта), а не временным окном, поэтому ретраи CRM безопасны.

> ⛔ Вебхук `tariff.activated` на **своё** назначение партнёру не отправляется — это было бы эхо на его собственный запрос. Результат целиком в ответе (`payment.expires_at`) и в `GET .../tariff`.

> ⛔ Отзыва назначения у партнёра нет: снимает тариф ApiPay по обращению.

Если сетка лимитов задана, допустимы только тиры из неё — иначе `422 tier_not_in_partner_grid`. Суточный лимит назначенного тарифа тоже берётся из сетки.

**Отказы:** `403 assignment_not_enabled`, `403 partner_not_active`, `403 production_access_required`, `409 test_organization`, `409 hard_limited_org` (жёсткое тарифное ограничение назначением не снимается), `409 custom_tariff_locked`, `409 tariff_payment_pending`, `422 tier_not_in_partner_grid`, `422 assignment_horizon_exceeded` (назначение увело бы дату истечения дальше чем на 12 месяцев вперёд).

### POST /organizations/{id}/tariff/invoice

Счёт на оплату тарифа для юрлица: синхронно формирует PDF с реквизитами покупателя и возвращает публичную ссылку `download_url`. Тело: `tier_id`, `period_months`, `buyer_bin`, `buyer_name`, опционально `contract` и `upgrade`.

> ⛔ `download_url` открывается **без авторизации**, по одному лишь адресу. Отдавайте её покупателю адресно, не публикуйте и не кладите в логи.

Оплата — банковским переводом; **автоактивации нет**, тариф выдаёт владелец ApiPay после поступления средств. Счёт виден в `GET .../tariff/payments` как `payment_method: invoice` с под-объектом `invoice`; переход платежа из `pending` в `completed` означает, что тариф выдан. Об активации приходит вебхук `tariff.activated`.

**Флаг `upgrade: true`** выписывает счёт на переход между тарифами: сумма считается как разница базовых цен (Start → Business — 15 000 ₸, а не 25 000), `period_months` обязан быть `1`, `tier_id` — целевой тариф. «С какого тарифа» определяет сервер по активному платному тарифу организации; передать это значение нельзя.

Тариф, с которого выполнен переход, приходит в поле `upgrade_from` — в объекте счёта, в истории платежей и в вебхуке `tariff.activated`. У обычного плана там `null`.

> ⛔ **`409 invoice_pdf_failed` повторять нельзя.** Счёт уже выписан: строки созданы, номер выделен, не собрался только PDF. Ретрай напечатает второй бухгалтерский документ. В теле — `invoice` с `payment_id` и `number`, без `download_url`; заберите номер и обратитесь в поддержку. Если ваш обработчик считает этот код повторяемым — снимите повтор.

**Отказы:** `400 downgrade_not_supported` (целевой тариф не выше текущего; понижение оформляется через поддержку), `409 invoice_locked`, `409 test_organization`, `409 organization_deleted`, `409 no_paid_tariff` (только при `upgrade` — переходить не с чего), `409 upgrade_invoice_pending` (неоплаченный счёт на переход уже есть, он же приходит в поле `invoice`), `409 custom_tariff_locked`, `422 invalid_tariff_plan`, `422 invalid_upgrade_plan`, `422 upgrade_period_not_supported`, `429 invoice_cooldown` (превышен лимит выписок за 24 часа — ждите `Retry-After`, он же `retry_after_seconds` в теле).

### GET /organizations/{id}/tariff/payments и /payments/{paymentId}

История платежей по тарифу мерчанта и карточка одного платежа.

### Индивидуальные условия

У мерчанта с договорными условиями тариф — это его базовый тариф плюс свои лимит и цена. Смена тарифа таким мерчантом отбивается `409 custom_tariff_locked` и оформляется поддержкой; **продление того же тарифа не блокируется** — это платёж, а не изменение условий. Состояние видно заранее по `is_custom` в `GET /organizations/{id}/tariff` — партнёрский каталог тарифов организацию не знает и признака смены не несёт.

## Лимиты запросов

| Группа | Лимит |
|--------|-------|
| Все эндпоинты Partner API | 120 запросов/минуту на партнёра |
| Авторизация кассира (`send-phone`, `verify-otp`) | 10 запросов/минуту на партнёра и организацию |

## Коды ошибок

| HTTP | Значение |
|------|----------|
| 401 | Неверный или отсутствующий `X-Partner-Key` |
| 403 | Нет доступа к запрошенному ресурсу |
| 409 | Конфликт — `no_process` (авторизация не начата или истекла), `already_connected` (организация уже подключена к Kaspi; чтобы сменить кассира, повторите `init` с `force: true`), `organization_identity_conflict` |
| 422 | Ошибка валидации — `invalid_phone`, `not_cashier` или `webhook_url` с приватным/внутренним адресом |
| 502 | Kaspi API недоступен — `sms_failed`, `organization_identity_unavailable` |

Коды тарифных ручек перечислены в разделе [Тарифы мерчантов](#тарифы-мерчантов) — у каждой ручки свой набор. Тело отказа всегда несёт `success: false`, `error` и `error_code` с одним значением; стройте логику по `error_code`.

## Выставление счетов от имени мерчанта

После онбординга используйте `X-API-Key` мерчанта (из шага 5) с обычным
API — `POST /api/v1/invoices`, подписки, возвраты и т. д.
См. [Начало работы](getting-started.md) и [Счета](invoices.md).
